# Add localization infrastructure
<!-- labels: enhancement,priority: P2,area: platform -->

## Problem

There is no localization anywhere: no `AddLocalization`, no `IStringLocalizer`, no `RequestLocalization`. Every user-facing string across 125 Razor components is hardcoded English.

The cost of this only goes up. Adding `IStringLocalizer` after another release of component growth is strictly more expensive than adding it now, and the infrastructure work is the same regardless of how many languages ever ship.

There is also a correctness dimension beyond translation: dates, numbers and the user-calendar-date rule in `AGENTS.md` all interact with culture, and that is not currently exercised by any test.

## Scope

- `IStringLocalizer` infrastructure with resource files and culture negotiation.
- Culture preference on the user profile, defaulting to the browser's.
- Extract strings surface by surface, prioritising Today, Inbox, Notes and the marketing pages.
- Culture-aware date and number formatting that preserves the existing rule: due dates are user-calendar dates, audit timestamps stay UTC.
- English plus one second locale to prove the pipeline end to end.

## Guardrails

- No behaviour change for English users.
- Do not localize enum values, analytics event names, cache keys or anything else the system reasons about — user-facing strings only.
- Missing translations fall back to English visibly in development, silently in production.

## Acceptance criteria

- [ ] Switching culture changes the UI language and persists across sessions.
- [ ] Dates and numbers format per culture while due-date semantics are unchanged.
- [ ] A missing resource falls back to English without throwing.
- [ ] Tests cover culture negotiation and the due-date/UTC boundary under a non-invariant culture.
