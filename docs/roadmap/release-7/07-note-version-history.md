# Add note version history
<!-- labels: enhancement,priority: P1,area: trust,area: workflow -->

## Problem

There is no revision, version or history entity anywhere in the domain. A note edit is destructive. For a tool whose promise is that captured knowledge stays useful, losing the earlier wording of a distilled note with no way back is a trust problem.

It also interacts with an existing requirement. `AGENTS.md` states AI-generated data must retain *"the original generated value separately from later edits"*. Today that is enforced per-field on individual entities; a revision timeline is the natural general home for it, and gets stronger as more AI features land.

## Scope

- Revision entity capturing content, title, timestamp and the reason for the change (user edit, AI generation, import, offline sync).
- Timeline UI on the note detail and editor pages.
- Diff between any two revisions.
- Restore a revision as a new revision, never as a destructive overwrite.
- Retention policy aligned with the existing `ArchiveRetentionService` approach.

## Guardrails

- Revisions are user-scoped like every other entity.
- Included in account deletion and in the data export.
- Bounded storage: a retention rule, not unbounded growth.
- Must not conflict with the existing rowversion concurrency handling — a stale edit still surfaces as a conflict rather than silently forking history.

## Acceptance criteria

- [ ] Editing a note creates a revision.
- [ ] A user can view, diff and restore any retained revision.
- [ ] AI-generated content is distinguishable from user edits in the timeline.
- [ ] Revisions are exported and deleted with the account.
- [ ] SQL Server integration tests cover retention and concurrency interaction.
